## 2. Git и деплой

- `origin` настроен на **dual-push**: `git push origin main` уходит сразу в два репозитория —
  `MIPTKBoy/SNREduOS` (рабочий, с него деплоит Vercel) и `sdakbarkhon/SNR-EduOS` (заказчика).
  `fetch`/`pull` — только из `MIPTKBoy`.
- Значит: **всё, что попало в `main`, заказчик видит сразу**, включая промежуточные коммиты.
- Секреты в репозиторий не коммитятся, включён GitHub push protection. Демо-пароли (§7) —
  исключение: они уже давно в документации репозитория и нужны для показа.
- `VERCEL_TOKEN` — в `apps/web/.env.local`. Для Vercel API **обязателен** `teamId`
  (`team_MYpBV2M3L64gwy59SGSL6QCG`, аккаунт `miptkboy`): без него API молча отдаёт пустой
  список деплоев, что легко принять за нерабочий токен.
- **`vercel.json` — строгий JSON, комментарии в нём невозможны.** Пояснения к кронам живут
  в комментариях самих route-файлов, не в конфиге.

## 3. Заморозка времени — три места

Демо-время заморожено навсегда на **29.07.2026 10:15 Ташкент** (`= 2026-07-29T05:15:00Z`).
Якорь стоит в СЕРЕДИНЕ 2-го урока (09:55–10:40), а не на стыке слотов, — иначе разные `>` / `>=`
в разных местах кода дают разный ответ, и подсветка «Сейчас» уезжает. **Не возвращать якорь на
границу слота** — этот круг уже проходили трижды, история в шапке `demo-date.ts`.

Живых мест три:

1. **Веб** — `apps/web/lib/demo-date.ts`, константа `FROZEN_AT_ISO`. Функции `getDemoNow()` /
   `getDemoNowMs()` безопасны и на клиенте, и на сервере; в БД не используются (`created_at`/
   `updated_at` пишет настоящий Postgres `now()`).
2. **Мобилка** — `apps/mobile-parent/app.json` → `expo.extra.frozenDate`, читается в
   `src/lib/appTime.ts` (там же фолбэк тем же значением).
3. **База** — колонка `schools.frozen_date` (`DATE '2026-07-29'`, миграция 173). На неё опирается
   триггер `trg_block_past_day_lesson_start`: он запрещает стартовать урок за **прошедший** день.
   Реальные школы (`frozen_date IS NULL`) не ограничены вовсе.

Четвёртая копия — константа `FROZEN_DAY` в `apps/web/scripts/restore-demo-lesson-shape.mjs`.
Меняешь дату — синхронизируй все четыре.

Сам замороженный день и всё, что позже, стартовать **можно**: заказчик показывает клиентам, что
уроки запускаются наперёд.

## 4. Форма демо-дня 1/2/3+ и снимок эталона

**Правило.** На 29.07 в каждой группе: 1-й урок `completed`, 2-й `in_progress`, 3-й и дальше
`scheduled`. По школе это **3 / 3 / 12**. Порядок записи при восстановлении жёсткий, `in_progress`
пишется последним — иначе триггер `trg_close_other_in_progress_lessons` гасит только что
поставленный статус.

**Снимок эталона** — таблица из миграции `179_demo_baseline_snapshot.sql`, наполняется скриптом
`apps/web/scripts/snapshot-demo-baseline.mjs`. Хранит идентификаторы четырёх типов:
`lesson`, `lesson_stage`, `lesson_material`, `homework`. На последнюю пересъёмку —
**126 уроков / 767 этапов / 248 материалов / 59 заданий**.

Почему снимок, а не отсечка по `created_at`: эталон создавался в два захода (29.07 и 30.07), а в
окне 05–08.08 вперемешку лежат и мусор от посетителей, и плановая работа. По времени они
неотличимы — дата снесла бы плановое вместе с мусором.

Чего в снимке **нет**: уведомления, родители, `curriculum_plan_topics`, `sandbox_projects`.
Ночной откат их не трогает.

**Важно:** после любой плановой правки демо-контента (добавили урок, этап, материал, задание)
**снимок надо пересъёмить**, иначе ближайшей ночью откат посчитает новое мусором и удалит.

## 5. Ночной откат и кроны

- Расписан **ровно один крон** — `vercel.json`: `/api/cron/restore-demo-lesson-shape`,
  `15 19 * * *` UTC = 00:15 Ташкент. Тариф Vercel даёт максимум два, остальные сняты с расписания.
- Каталогов маршрутов под `apps/web/app/api/cron/` четыре (`restore-demo-lesson-shape`,
  `homework-review-process`, `morning-lesson-cycle`, `rag-process-queue` в `_lib`-соседстве) —
  **в расписании только первый**. Остальные вызываются вручную, если понадобятся.
- Логика отката — `app/api/cron/_lib/restore-demo-shape.ts`, там же расписан жёсткий порядок фаз.
  `GET` и `POST` ведут в один handler: Vercel Cron всегда шлёт `GET`, на этом здесь уже дважды
  ломались кроны.
- Перед любым запуском отката — **холостой прогон**: `apps/web/scripts/check-demo-rollback-dry.mjs`.
  Ожидание — ноль удалений. Хоть одно — не применять, разбираться.

⚠️ **Ловушка, из-за которой уже терялись данные.** PostgREST режет ответ на **1000 строк**
(`db-max-rows`). Любой `.select()`, который может вернуть больше, обязан идти через `.range()`
с постраничным чтением и сверяться с точным `count`. Именно на этом откат однажды прочитал
1000 из 1217 строк эталона и удалил остальное как «не из снимка» (коммит `61d6820`).

**Что нашла приёмка Z.2.11 и что осознанно НЕ чинилось:**

1. **Школу нельзя удалить** — 55 из 58 внешних ключей на `schools` объявлены `NO ACTION`.

2. **Порядок шагов нигде не подсказан** — пустая школа встречает админа пустыми списками,
   правильная последовательность (предметы → группы → учителя → назначения → ученики)

3. **Родитель не входит паролем на вебе** — только телефон + код; пока нет SMS-провайдера

4. **У админа школы нет своего логина в интерфейсе** — он существует только внутри служебного
   адреса, в списке админов не показан.
5. **Куратор группы** — поля в реальных школах нет, но колонка `groups.teacher_id` и права
   куратора остались; разделение прав отложено в Z.4.

**Осталось:**

- **Z.3 — разделение режимов.** Реальное время и автостарт уроков для не-демо школ. Сюда же два
  блокера, которые нельзя оставлять при живых пользователях реальной школы:
  (а) `claim_demo_slot()` не фильтрует по школе — как только в реальной школе появится первый
  ученик, демо-кнопка начнёт выдавать анонимным посетителям его живой аккаунт вместе с паролем
  открытым текстом; (б) `getDemoNow()` глобальный — реальная школа получит замороженные 29.07.
  **Боевая эксплуатация реальной школы — только после Z.3.**
- **Z.4 — изоляция контента.** RLS-разделение по школам, включая права куратора:
  `is_curator_teacher()` про школу не знает вовсе (только `subject_slug IS NULL`) и входит в
  SELECT-политику `lessons` — переписывать её значит тронуть видимость уроков у всех.
  Сюда же мультипредметность учителя.
- **Z.5** — такого шага **нигде в репозитории не описано**. Если он существует, он живёт только
  в переписке; в `plan-z2-admin-rebuild.md` и `resheniya_2.md` перечислены Z.1–Z.4.

## 11. Рабочие правила, выросшие из этой работы

Они появились после аварии, в которой ночной откат удалил 49 уроков со всем содержимым.
Соблюдать без напоминаний:

1. **Холостой прогон перед каждой записью в базу.** Показать, что именно будет создано/изменено/
   удалено, и только потом писать.
2. **После каждого шага — сверка цифр.** Сколько ожидали, сколько получилось. Любое расхождение —
   **остановка и показ**, а не «поправлю по ходу».
3. **Пагинация обязательна** для любой выборки, способной перевалить за 1000 строк, плюс сверка с
   точным `count` (§5).
4. **Живая проверка — во второй, пустой школе**, не в демо. Всё созданное при проверке — убирать
   за собой (кроме самой школы: её удалить нельзя, см. §10).
5. **Один заход — один коммит и один пуш.** После пуша один раз проверить статус деплоя, без
   циклов ожидания.
6. **Демо-контент трогать только по явной задаче**, и после любой правки — пересъёмка снимка (§4).
7. **Учётные данные на проде не трогать**: пароли не подбирать, хеши не сопоставлять,
   `auth.users` ради паролей не читать. Максимум — подготовить текст SQL заказчику.
8. **Бакеты не открывать публично.** Ссылки на приватные файлы — только подписанные.

## 12. Известные хвосты (не блокируют демо)

- **RAG-пайплайн стоит.** `lesson_stage_embeddings` пуста, очередь растёт — крон
  `rag-process-queue` в расписании не стоит (§5). Код retrieval рабочий, но контекста не находит.
- **`projects.subject_id` — схемный пробел**: у `projects` нет FK на предмет, только текстовый
  `projects.subject` из мусорного `groups.subject`. Сейчас 0 оценённых проектов → не проявляется.
- **Ротация `SUPABASE_SERVICE_ROLE_KEY`**: проект на legacy-ключах (`eyJ...`), поштучная ротация
  невозможна — только roll JWT-секрета целиком (разлогинит всех). Чистый путь — переезд на
  `sb_secret_...`, требует ревизии всех серверных роутов.
- **Middleware зовёт `getSession()` вместо `getUser()`** — Supabase пишет предупреждение на каждый
  запрос. RLS всё равно защищает.
- **H5P**: `h5p.eduos.snruz.uz` не резолвится, `/library` отдаёт 307. Тип `h5p` в заданиях
