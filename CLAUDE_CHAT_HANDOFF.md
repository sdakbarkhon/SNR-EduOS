## 1. Что это за проект

Учебная платформа для частной школы в Ташкенте: расписание, уроки с этапами, домашние
задания, оценки, посещаемость, чаты, объявления, помощник на основе модели ИИ. Пять
ролей: ученик, учитель, родитель, администратор школы, суперадминистратор.

Монорепо на pnpm + Turborepo. Состав и размер (файлы `.ts`/`.tsx`, без служебных
каталогов):

| Часть | Что это | Файлов | Состояние |
|---|---|---|---|
| `apps/web` | Основное веб-приложение, Next.js 15 (App Router) | 628 | живое, правится ежедневно |
| `apps/mobile-parent` | Приложение для родителей, Expo SDK 54 | 158 | живое, последняя правка 23.08 |
| `packages/core` | Общий слой: типы, запросы к базе, переводы | 42 | живое |
| `apps/mobile` | Ученическое приложение | 29 | **заморожено навсегда**, из проверки типов исключено |
| `apps/h5p` | Отдельное приложение под интерактивный контент H5P | 14 | последняя правка 13.08 |
| `packages/ui-tokens` | Цвета и размеры одним местом | 1 | не развивается с 16.06 |

База, авторизация, файлы и живые обновления — **Supabase** (проект `qaljcmkkajqyawccxetq`,
Франкфурт). Хостинг веба — **Vercel**, проект `snr-edu-os-web`, домены `eduos.snruz.uz` и
`snr-edu-os-web.vercel.app`.

**Регион исполнения — Франкфурт (fra1).** Замерено живьём по заголовку ответа прода:
`x-vercel-id: hkg1::fra1::…` — первая метка это пограничная точка сети, через которую
зашёл запрос, вторая (`fra1`) — где отработала функция. В настройках проекта при этом
стоит `iad1`, а в `vercel.json` — `fra1`; действует то, что в файле. База тоже во
Франкфурте (`aws-1-eu-central-1`) — приложение и база в одном городе.

**Родительское приложение доезжает до телефона по воздуху, а не через магазины.**
Аккаунт Expo/EAS `snreduos`, slug `snr-eduos-parent`, канал **`preview`**,
`runtimeVersion: "exposdk:54.0.0"` одной строкой на обе платформы. iOS — только через
**Expo Go** (настоящей `.ipa` нет и не будет без Apple Developer), Android — тем же
каналом или отдельным APK из `eas build`. Приложение само зовёт обновление при холодном
старте. **Публиковать только по слову заказчика.** Прежний аккаунт `new_assassin`

**Перевод демо-содержимого лежит не в общем словаре** (23.08). 152 строки заготовок на

`packages/core/src/i18n` эти строки намеренно не клали — они нужны одному только демо.

### Команды

Все из корня репозитория:

```bash
pnpm install --frozen-lockfile && pnpm type-check && pnpm lint:hooks && pnpm turbo run build --filter=web
```

Это предпушевой набор целиком, занимает около двух минут. Последняя команда — буквально
та же строка, которую выполняет Vercel.

- `pnpm type-check` — `turbo run type-check --filter=!mobile`. **Исключение `mobile`
  обязательно:** замороженное ученическое приложение даёт 5 ошибок типов на чистом
  дереве, и без фильтра предпушевая проверка не проходит никогда. Объяснить это прямо в
  `package.json` нечем — там строгий JSON без комментариев. Поэтому `turbo run type-check`
  напрямую, минуя `pnpm`, снова упрётся в те же пять ошибок; это не регрессия.
- `pnpm lint:hooks` — единственная защита от ошибки React #310. Правило про зависимости
  хуков отключено намеренно, ловятся только настоящие нарушения.
- `gen:types` в корне зовёт Supabase CLI с ключом `--local` и **на этой машине не
  работает**: CLI поднимает контейнер, а Docker не установлен. Как обходить — §6.

### Тесты

Тестов на JS/TS в проекте **нет ни одного**: ни файлов `*.test.*`, ни скрипта `test` ни в
одном `package.json`. Есть четыре SQL-теста на pgTAP в `supabase/tests` (изоляция по
ролям, изоляция по школам, оценки, поля этапов). Запускаются только в локальном стеке
Supabase: **в живой базе расширение `pgtap` не установлено**, там их не прогнать.

## 3. Заморозка времени

**Правило одно: «сейчас» школы = `schools.frozen_date`.** Пусто — настоящее время; дата —
время замирает на этой дате в 10:15 по Ташкенту.

Где задаётся и читается:

- `apps/web/lib/school-time.ts` — **единственный источник времени в вебе**. Прежний
  `lib/demo-date.ts` удалён.
- `packages/core/src/utils/schoolTime.ts` — то же для общего слоя.
- В базе: `fn_block_past_day_lesson_start()` — запрещает стартовать урок за прошедший
  день; при пустой заморозке выходит сразу, то есть боевую школу не ограничивает.

**Якорь 10:15 не трогать.** Это середина второго урока (09:55–10:40). До 07.08 стоял
10:50 — ровно на границе третьего, и сравнения `>=` против `>` в разных местах давали
разный ответ: урок то считался идущим, то нет. В файле стоит прямая надпись «не возвращать
якорь на границу слота».

**Опираться на признак демо, куку демо-сессии или демо-аренду нельзя.** У демо-школы есть
настоящий ученик `sherzod_10`, он входит обычным логином и куки не получает — любая такая
реализация отдала бы ему реальное время.

**Проверено 23.08:** заморозка не протекает в боевую школу — у неё `frozen_date` пуст, и
все пути отдают настоящее время. Отдельная, не связанная с заморозкой болезнь: **в
нескольких местах «сегодня» считается по поясу браузера или сервера, а не по Ташкенту** —
календарь посещаемости и месяц уроков у учителя. На границе суток и месяца промахиваются
на день. Это касается **боевой** школы, а не демо.

Часового пояса у школы в базе нет вовсе — Ташкент (+5) вбит константой примерно в
тридцати файлах.

### Как логин превращается в адрес

Адрес входа синтетический: `<логин в нижнем регистре>@<домен роли>`. Домены заданы одним
файлом `packages/core/src/auth/username.ts`: `students.snr.local` (по умолчанию),

`demo.snr.local` (пул демо-аккаунтов).

Роль при входе не спрашивается, а подбирается перебором: строка с `@` пробуется как есть,
иначе по очереди ученик → учитель → админ → родитель, и в конце — демо-домен, если логин
начинается на `demo_student`/`demo_teacher`.

### Вход родителя по телефону

Четыре цифры, срок пять минут, до пяти попыток, повтор не чаще раза в минуту,
одноразовость. В базе лежит хеш от «код:телефон». Провайдер — Eskiz.uz, но **на проде его
переменных нет вовсе**: в настройках Vercel заведено шесть имён, `ESKIZ_*` среди них
отсутствуют. Значит настоящий код родителю **не уходит** — админ диктует его голосом из
карточки родителя.

**Открытая копия кода живёт ровно столько же, сколько сам код** (правка 22.08). Она
обнуляется во всех пяти точках, где код гаснет: выдан новый на тот же номер, просрочен,
кончились попытки, успешный вход, карточка админа наткнулась на истёкший. Накопленные
13 мёртвых копий вычищены 22.08. **Сейчас в таблице 13 строк и ни одной открытой копии.**

Ограничения по адресу (миграция 219): выдача кода 60 в час, проверка 120 в час, взятие
демо-слота родителя 10 в час. Счётчики в `rate_limit_counters`, сейчас таблица пуста.

### Демо-вход — четыре пути

1. **Кнопка «Демо» на `/login`** — модалка с шестью карточками (ученик 3/7/10 класса и
   пять предметников). Зовёт функцию базы `claim_demo_slot`, та требует, чтобы демо-школа
   была **ровно одна**, и во всех трёх ветках фильтрует по её идентификатору. Проверено
   повтором отбора: кандидатов 29, все из демо-школы; **учителя боевой школы с теми же
   предметами отсечены**.
2. **Мобильное приложение родителя** — маршрут `/api/demo/claim-parent`, та же функция,
   не более 10 запросов с адреса в час. С 26.08 вход внутри маршрута тоже без пароля;
   ответ наружу не изменился (`access_token`, `refresh_token`, ключ аренды), поэтому
   приложение править не пришлось и обновление выкладывать не нужно.
3. **Кнопка «Посмотреть демо» на `/parent` (веб)** — **отдельный путь, идущий мимо всего
   механизма**: ищет родителя по жёстко вписанному номеру `+998912345678`, аренду не
   берёт, признак демо не проверяет. Сегодня номер принадлежит демо-родителю, и на этом
   всё держится. Единственный замок — глобальная уникальность телефона.
4. **Вход через Google** — не демо: ищет человека по `google_email` среди всех ролей.
   Заполнен он ровно у одного родителя демо-школы.

**В мобильном приложении демо-вход теперь оставляет след — и это несущая деталь**
(23.08). Ключ аренды, который `claim-parent` возвращал и приложение выбрасывало,
сохраняется в защищённое хранилище телефона. Из этого следуют две вещи. Первая: аренда
наконец продлевается — до 23.08 продление не шло вовсе, и демо-место отваливалось через
15 минут посреди показа. Вторая: наличие ключа — **единственный признак «мы в демо»** в
приложении. По нему разделы, у которых настоящих данных нет, показывают выдуманные;
у родителя, вошедшего по номеру телефона, там по-прежнему экран «Скоро». Признак гаснет
при выходе — иначе он пережил бы его и настоящий родитель увидел бы выдуманное как своё.

**Не опираться вместо этого на заморозку школы.** «Школа заморожена» и «вошли через
демо» — разные вещи; сегодняшнее совпадение случайно, потому что единственный родитель
демо-школы и есть демо-родитель.

Аренда демо-слота живёт 15 минут от последней активности.

**«Часть слотов выдаётся с нерабочим паролем» — утверждение СНЯТО 26.08 как
неподтверждённое.** Сверка хешей по живой базе (проверка известного литерала через
`extensions.crypt`, без подбора и без входа) дала:

* **0 расходящихся аккаунтов из 36** — 30 учеников, 5 предметников, 1 родитель. У всех
  `password123` / `parent2026` открывает учётку. Заодно исключены: неподтверждённая
  почта, бан, пометка удаления, отсутствие записи в `auth.identities` — по нулю;
* **21 короткая аренда из 174** (не 31 из 173, как считалось). Короткие — действительно
  неудачные входы: все длятся 0.000–0.349 секунды, десять ровно 0.000, и 13 из 21
  сопровождаются новой арендой в пределах пяти секунд, девять — уже на другой аккаунт;
* **последняя короткая аренда — 08.08.2026 04:58 UTC.** С 09.08 по 26.08 — 39 аренд без
  единой неудачи;
* **причина тех отказов НЕ УСТАНОВЛЕНА.** `auth.audit_log_entries` пуст (0 записей),
  логов Vercel за те дни нет, `auth.users.updated_at` в качестве замены не годится —
  Supabase двигает его при каждом входе.

**Пароль из демо-входа убран совсем (26.08).** Все три демо-входа получают сессию
одноразовой ссылкой: служебный клиент выпускает `token_hash` через `generateLink`,
вызывающий меняет его на сессию через `verifyOtp`. Общая часть — `lib/demo-otp.ts`.
Литерал в `claim_demo_slot` остался в базе как есть и просто не используется; миграции
для этого не понадобилось.

Повтор с другим слотом (до трёх попыток) **оставлен**, но защищает уже не от пароля —
его в обмене нет, — а от аккаунта, под которым сессия не выдаётся в принципе: бан,
пометка удаления, пустой адрес, потерянная `identity`. Сегодня таких нет ни одного.

**Одна сессия на аккаунт.** При каждом входе все прежние строки сессии этого пользователя
удаляются, а посредник на каждом запросе проверяет совпадение — не совпало, выкидывает с
пометкой «сессию заняли». При сбое проверки считается, что сессия годная (сознательно,
чтобы недоступность базы не разлогинила всех). Демо-вход **тоже** регистрируется, то есть
гость вытесняет того, кто сидел под тем же демо-аккаунтом; комментарий в коде мобильного
маршрута утверждает обратное и **врёт**.

### Что может и чего не может суперадмин

Пять экранов и тринадцать действий: школы, админы школ, расходы на ИИ, журнал, настройки,
вход в школу на просмотр. Все идут через служебный ключ, поэтому запрет на запись их не
задевает.

**После миграции 222 записи в школьные таблицы под собственным токеном у него нет.**
**156 сужающих правил на 59 таблицах** (замер 24.08; на момент самой миграции было
152 на 58 — прибавились те, что заводили 223–225) вида
«либо перед нами не суперадмин, либо запись разрешена списком». **Список разрешённого
пуст** — это решение заказчика. Незакрытых таблиц не осталось: разность «пускает, но не
прикрыто» пустая.

Читать он по-прежнему может всё: 117 правил чтения на 62 таблицах не тронуты.

**Журнал действий суперадмина (миграции 220–221) заполняется.** На 24.08 в
`superadmin_journal` **10 записей** — до этого числа он стоял пустым, и в прошлой версии
файла так и было записано.

## 6. Миграции

**Последний номер файла — 225.** Файлов в каталоге 220 (219 `.sql` и один посторонний
`164_REPORT.md`), в двух форматах имён: 69 с датой и 150 с простым номером.
**Следующий свободный номер — 227.**

**226 НАПИСАНА, НО НЕ ПРИМЕНЕНА** (26.08) — `226_lesson_subject_required.sql`, ждёт ручного
применения заказчиком через Dashboard. Что она делает:

* **`lessons.subject_id` становится NOT NULL.** Урок без предмета не исчезал и ошибки не
  давал — он переставал быть виден ТОЛЬКО учителю (правила доступа сужают уроки
  предметника через `subject_id`), а ученик, родитель и админ видели его как обычно;
* **внешний ключ `lessons_subject_id_fkey` меняется с `ON DELETE SET NULL` на
  `ON DELETE RESTRICT`.** Раньше удаление предмета молча обнуляло предмет у всех его
  уроков — на этом висело 126 уроков демо и 2 боевой;
* если в базе окажется хоть один урок без предмета, миграция **падает с текстом и числом**,
  а не проставляет что-то по своему усмотрению.

**Отсюда: предмет, у которого есть уроки, БОЛЬШЕ НЕ УДАЛЯЕТСЯ.** Это принятая заказчиком
цена, а не поломка. Если удаление отказывает — искать причину не надо, она здесь. Два
рубежа: гвард в `admin-api.ts` (`BLOCKED_SUBJECT_IN_USE` со счётом уроков, заданий и
планов) и сам RESTRICT; второй разбирается отдельной веткой по имени ограничения и даёт
фразу `adminErrors.subjectHasLessons`, а не общее «есть связанные записи».

Прогон в транзакции с откатом (26.08): урок без предмета не создаётся, обнулить предмет у
существующего нельзя, предмет с уроками не удаляется (код 23503), предмет БЕЗ уроков
удаляется по-прежнему, 128 существующих уроков не тронуты, страж останавливает миграцию на
базе с уроком без предмета. Во всех отказах затронуто 0 строк.

`createLesson` в общем слое больше не принимает пустой предмет: тип обязательный, плюс
отказ «У урока должен быть предмет». Все скрипты, создающие уроки прямой вставкой
(`create-schedule-week`, `regenerate-jul27-aug2`, `restore-demo-lessons`), предмет
передают — NOT NULL их не ломает.

**225 ПРИМЕНЕНА** (проверено 24.08 по самой схеме, а не по реестру): правило правки
посещаемости содержит `marked_by IS NULL`, замок `fn_lock_teacher_marks` пропускает
машинную отметку, `fn_auto_end_lessons` отбирает уроки по
`ends_at <= now() - interval '5 minutes'`. 224 тоже применена: триггера и функции рассылки
про создание урока в схеме нет вовсе.

**Реестр применения не является источником правды.** В `supabase_migrations.schema_migrations`
193 строки (124 коротких номера и 69 с датой), максимальная короткая версия — **214**, но
в схеме присутствуют объекты всех миграций вплоть до **225**. Всего файлов, не записанных
в реестр, — **27**: 114, 138–141, 162–164, 175–182 и все 215–225. Причина: часть миграций
применялась напрямую, а реестр пишет только `apply-migration.mjs`. Есть и обратный
случай — версия `146` записана, а файла такого нет ни в дереве, ни в истории.

**Следствие: `supabase db push` на этой базе запускать нельзя, а «последнюю применённую»
по реестру читать бессмысленно.** Сверяться надо со схемой — `pg_get_functiondef`,
`information_schema`, `pg_trigger`.

Применение: `node apps/web/scripts/apply-migration.mjs supabase/migrations/226_имя.sql`.
Строку реестра в тело файла **не вписывать** — скрипт добавляет её сам и без защиты от
повтора. **Применение к проду санкционирует заказчик.**

**С 26.08 скрипт спрашивает подтверждение**: показывает файл, версию, число строк, состав
команд и шапку миграции, ждёт «да». Флага «пропустить вопрос» нет намеренно — по всему
репозиторию его не зовёт ни другой скрипт, ни приложение, ни крон.

## 7. Что работает само

### В базе — три задания pg_cron

| Задание | Расписание | Что делает |
|---|---|---|
| `auto-start-lessons` | каждую минуту | переводит урок в «идёт», если начало было в последние 5 минут; закрывает этап «Начало» |
| `auto-end-lessons` | каждую минуту | закрывает урок **через 5 минут после звонка** (225), отмечает этап «Итог», **ставит «Пропуск без причины» всем неотмеченным** и запирает все отметки урока. Прогул ставится без автора — по этому признаку учитель его и правит |
| `cleanup-expired-announcements` | 02:00 UTC | удаляет объявления, у которых вышел срок |

За сутки 2881 запуск, **ошибок ноль** (перепроверено 24.08). Обе минутные функции
отбирают уроки только тех школ, где включён автостарт, — то есть **работают исключительно
по боевой школе**.

**Расширения `pg_net` в базе нет** — ни одно задание не может сходить по сети, вся
машинерия внутри SQL.

### На Vercel — два крона

1. **`/api/cron/restore-demo-lesson-shape`, 19:15 UTC** — ночной откат формы уроков
   демо-школы. Работает с 07.08.
2. **`/api/cron/rag-process-queue`, 02:00 UTC** — разбор очереди векторов, обе школы,
   до 60 записей за проход. Возвращён 26.08 (был удалён 08.08, и очередь полмесяца
   никто не разбирал).

Оба включены и привязаны к последнему деплою. Расписание разведено намеренно: с учётом
точности ±59 минут откат идёт в окне 19:15–20:14 UTC, разбор — в 02:00–02:59 UTC, между
ними около шести часов при потолке функции в пять минут. Пересечься не могут, и сбой
одного не трогает другой — это разные функции с разными запусками.

**Ловушка, стоившая пяти неработавших кронов:** Vercel читает `vercel.json` **из корневой
папки проекта, а она `apps/web`**. Корневой `vercel.json` в репозитории — мёртвый файл, он
не читается вообще. Пока расписание лежало в нём, ни один крон не выполнился ни разу.

Вторая ловушка того же ряда: **Vercel Cron всегда шлёт GET**. Маршрут, экспортирующий
только POST, будет молча получать 405.

Третья — и здесь справка САМА врала до 26.08, поправлено по документации Vercel и по
ответу их API:

* **мест не два, а СТО** на проект, и на hobby, и на pro. Занято два, свободно 98 —
  экономить их незачем;
* настоящее ограничение бесплатного тарифа — **частота: не чаще раза в сутки**. Выражение
  вроде `0 * * * *` или `*/30 * * * *` **роняет выкладку** с ошибкой «Hobby accounts are
  limited to daily cron jobs. This cron expression would run more than once per day». Вот
  что на самом деле блокировало деплой, а не количество;
* точность на бесплатном тарифе **±59 минут**: `0 2 * * *` сработает где-то между 02:00 и
  02:59 UTC;
* **потолок времени функции — 300 секунд**, и по умолчанию, и максимум (fluid compute
  включён по умолчанию). Прежняя запись «60 секунд» была неверной.

Нужны более частые запуски — это pro (~$20/мес) либо сторонний планировщик, дёргающий
маршрут с `CRON_SECRET`.

**Ещё два маршрута крона существуют, но в расписании их нет:**
- `homework-review-process` — рабочий разбор очереди ИИ-проверки домашних работ; зовётся
  только руками. Сейчас не аукается: очередь пуста.
- `morning-lesson-cycle` — заглушка, отключена 05.08, отдаёт «пропущено».

### По событию из браузера

В общем слое ровно два вызова «выстрелил и забыл», оба работают **только в браузере**:

- `/api/rag/process-stage` — считает векторы этапа для помощника. Зовётся из трёх мест:
  создание этапа, правка этапа, запись вопросов квиза.
- `/api/stage-media/generate` — генерация картинки к этапу. Зовётся из одного места —
  создание этапа.

**Скрипты наполнения этих путей не исполняют** — они пишут в базу напрямую. Это ключевая
особенность: всё, что залито скриптами, остаётся без векторов и без картинок.

## 10в. Дата и время: один помощник на весь продукт

**Сведено 26.08.2026.** Разбор даты живёт в **`packages/core/src/utils/date.ts`** — это
единственное место, где записано смещение Ташкента (+5 часов). Своих `TZ_MS` не заводить:
на 26.08 их было ВОСЕМНАДЦАТЬ, включая четыре собственные функции ключа дня.

**Чем болело.** Момент времени брался верно (школьное «сейчас»), а разбирался через
`getFullYear`/`getMonth`/`getDate`/`getDay` — то есть в поясе среды, а на Vercel это UTC.
Каждые сутки **с 00:00 до 04:59 по Ташкенту** день расходился, на границе месяца — месяц.
Учитель, открывший расписание в 01:00 первого сентября, запрашивал АВГУСТ и видел пустой
список. Проверено перебором: ровно пять часов из двадцати четырёх.

**Что умеет помощник:**

| функция | что даёт |
|---|---|
| `tashkentDayKey(v)` | «YYYY-MM-DD»; принимает строку, число и `Date` |
| `tashkentParts(v)` | `{year, month (1–12), day}` |
| `tashkentMonthKey(v)` | «YYYY-MM» |
| `tashkentWeekday(v)` | день недели, нумерация как у `getDay()` (0 — воскресенье) |
| `tashkentHour(v)` | час суток 0–23 |
| `isSameTashkentDay(a, b)` | один ли это день |
| `tashkentWeekMonday(v)` | понедельник недели, «YYYY-MM-DD» |
| `tashkentDayOfYear(v)` | номер дня в году |
| `tashkentDayBoundsUtc(v)` | границы суток в UTC — для `.gte()` / `.lte()` |
| `tashkentMonthBoundsUtc(y, m)` | границы месяца в UTC |

Плюс прежние `formatTime`, `formatDate`, `formatDateTime`, `APP_TIME_ZONE`.

**Календарные сетки строятся полуночью UTC**, а не локальной: ячейка — это позиция, а не
момент, и у полуночи UTC ключ дня не съезжает ни в одном поясе.

**Три копии смещения остались, и это не недоделка:**

* `apps/web/app/api/cron/_lib/restore-demo-shape.ts:63` — ночной откат и крон, запретная зона;
* `apps/web/lib/school-time.ts:115` `tashkentDay` — заморозку времени трогать нельзя;
* `apps/web/app/parent/(app)/_ui/format.ts:34` — решение заказчика: экраны родителя закрыты

**Отдельно ждёт:** 22 вызова `toLocale*` без указания пояса — экраны оценок, админки,
суперадмина и учебных планов. Список в `resheniya_3.md` за 26.08.

## 11. Что нельзя трогать и почему

- **`groups.subject`** захардкожена в `'programming'` у всех групп с миграции 97 и
  реальный предмет не отражает. Предмет резолвить через `lessons.subject_id → subjects`.
  То же с `course_materials.subject`.
- **У `lessons` нет колонки `teacher_id`.** Предметник урока — только через
  `subject_id → subjects.teacher_id`. `groups.teacher_id` — это куратор.
- **`teachers.subject_slug = NULL` означает «куратор»**, и на этом висит видимость уроков
  в демо-школе. Массовая простановка слага сузит видимость, массовое обнуление расширит.
- **Служебный ключ не имеет `auth.uid()`.** Под ним `current_school_id()`,
  `current_teacher_id()`, `current_student_id()` дают пусто — отсюда «null value in column
  school_id» и затёртые авторы оценок. Под служебным ключом школу и авторские поля
  задавать явно. Этот класс ошибок ронял скрипты уже дважды.
- **Триггер личных чатов на `subjects`** при каждом изменении учителя пробегает всех
  учеников группы и заводит чаты. Массовых правок по `teacher_id` не делать.
- **Публичные адреса файлов не использовать** — все бакеты закрытые. Только подписанные
  ссылки, и лучше через общую функцию.
- **Права по умолчанию открывают анониму каждую новую функцию.** В базе стоят действующие
  «права по умолчанию» на схему, выдающие право выполнения ролям anon и authenticated.
  Значит **любая новая функция автоматически доступна с улицы**, без единой строчки
  выдачи в миграции. Это корень проблемы, которую закрыла 223, и он остаётся.
- **Мёртвый, но безвредный код:** блокировка правки из демо-сессии принудительно
  отключена после миграции 132 — это не баг. Ключ перевода `legendLate` намеренно не
  удалён: его использует замороженное ученическое приложение.
- **Чего в схеме нет:** таблиц `profiles` и `parent_children` (правильное имя —
  `parent_students`), колонок `students.is_active`/`is_deleted` (есть `status`), статуса
  посещаемости «опоздал».

### Ловушки, на которых уже спотыкались

- **React #310 от смены дерева в оболочке.** Ранний возврат с другим деревом для
  полноэкранного урока уничтожал поддерево: урок монтировался дважды, подписки
  дублировались. Лечение — одно дерево, обёртки с `display:contents`.
- **Гидратация ломалась от ветвления Fragment↔div** в компоненте, оборачивающем всё
  дерево. Сейчас всегда один и тот же `div`, меняются только стили.
- **`router.refresh()` ненадёжен в Next 15** — не перезагружал серверные компоненты; в
  двух местах заменён на полную перезагрузку страницы.
- **Молчаливое глотание ошибок запросов** дважды давало прод-баги («Выходной» вместо
  расписания, пустые оценки). Заменено на `lib/safe-query.ts`, который логирует и
  возвращает признак неудачи.
- **Пагинация обязательна** для выборок, способных перевалить за 1000 строк, со сверкой с
  точным счётчиком. Это буквально причина аварии 08.08: постраничности не было, PostgREST
  молча отдал 1000 из 1217, и механизм снёс 49 эталонных уроков и 75 материалов.
- **Границы месяца и суток** строить явно по Ташкенту, а не конструктором даты: на
  сервере в UTC месяц начинался в 05:00 первого числа.
- **`typeof window` в общем слое** валит проверку типов монорепо — там нет DOM. Проверять
  через `globalThis`.
- **Свой подсчёт среднего балла не писать** — правило одно, в
  `packages/core/src/utils/gradeAverage.ts` (§10a). Семь независимых реализаций уже
  разошлись между собой; восьмую заводить нельзя.
- **Две связи на одну таблицу ломают короткое вложение в запросе.** Если у таблицы ДВА
  внешних ключа на одну и ту же, PostgREST не может выбрать, какой имеется в виду, и
  отвечает **300 PGRST201** на весь запрос. `safeQuery` глотает это и подставляет пустой
  список — экран показывает «ничего нет», не жалуясь. Так полтора месяца молчал блок
  объявлений на дашборде учителя (24.08). Лечение — имя ключа прямо в запросе:
  `group:groups!announcements_group_id_fkey(name)`. Пар с двумя ключами в базе три:
  `announcements → groups`, `homework_submissions → teachers`, `parents → auth.users`;
  вложение по короткому имени было только в первой.

- **Порядок слов в ФИО.** У семи карточек демо-школы имя стояло вторым словом, и код
  разбирал их по-разному: `realChild.ts` брал первое слово, приветствие главного экрана
  — последнее, специально под перевёрнутый порядок. 23.08 база и оба места приведены к
  одному правилу — **имя первым словом**. Правку кода и правку данных вести только
  вместе: одна без другой начинает здороваться фамилией.
- **Замок на отметках заводила машина.** Одна и та же болезнь дважды: у оценок (лечила

### Где копии кода уже расходились

Это системная болезнь проекта: журнал насчитал шесть случаев в одном ряду, отдельно
задокументировано ещё не меньше семи. Живые расхождения на сегодня — вычисление класса по
названию группы (три копии, две с другим значением по умолчанию), иконки инструментов,

**Прежде чем править логику — поиск по всему репозиторию.** Велика вероятность, что рядом
живёт вторая реализация того же.

Дважды рассинхрон `pnpm-lock.yaml` с `package.json` валил все деплои — поэтому
`pnpm install --frozen-lockfile` входит в предпушевой набор.

## 13. Как работать

Правила выросли из аварий, а не из вкуса.

1. **Холостой прогон перед любой записью в базу.** Показать, что будет создано, изменено
   или удалено, и только потом писать. Все скрипты в репозитории устроены так: без флага —
   прогон, запись по `--confirm`/`--apply`.
2. **После каждого шага — сверка чисел.** Сколько ожидали, сколько вышло. Любое
   расхождение — остановка и показ, а не «поправлю по ходу».
3. **Правку схемы проверять прогоном с откатом** на живой базе: `BEGIN … ROLLBACK`, внутри
   применить миграцию и проверить и то, что закрылось, и то, что должно продолжать
   работать. Ошибки прав при правке и удалении **не бросаются, а дают ноль строк** — в
   пробах обязательно печатать число затронутых строк, иначе проба соврёт «прошло».
4. **Пагинация и сверка со счётчиком** для всего, что может перевалить за 1000 строк.
5. **Локальная сборка перед отправкой**, полным набором из §1. Сборка «как есть» ничего не
   доказывает, если в дереве лежат незакоммиченные файлы: они подхватятся с диска, а на
   Vercel их не будет. Так дважды падали все деплои.
6. **Один заход — один коммит и один пуш.** После пуша один раз проверить статус выкладки,
   без циклов ожидания и без пауз.
7. **Демо-контент трогать только по явной задаче**, и после любой правки — пересъёмка
   снимка (§4).
8. **Учётные данные на проде не трогать:** пароли не подбирать, `auth.users` ради паролей
   не читать.
9. **Живая проверка — во второй, боевой школе**, не в демо. Мусор после проверки убирать
   руками: школу удалить можно, но это уносит всё каскадом.
