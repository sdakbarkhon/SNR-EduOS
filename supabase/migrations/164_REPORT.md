# Отчёт: дубли/битые title в chat_threads (прод, read-only)

Проверено `SELECT`-запросами через `$DATABASE_URL` (сервис-роль, только чтение,
без единой записи). Дата проверки — перед написанием `164_repair_chat_titles_with_dedup.sql`.

## Главный вывод: это не дубли

Изначальное предположение задачи («2 треда на группу — один битый, один
нормальный, потенциальный дубль после починки title») подтвердилось только
частично. По факту:

- Миграция 81 **намеренно** создаёт **два разных** group-треда на одну группу:
  ученический (`title = "<имя группы>"`) и родительский
  (`title = "<имя группы> — Родители"`, см. `81_..._parent_group_threads.sql`,
  строки 94 и 150). Unique-индекс `chat_threads_group_title_unique_idx` был
  ослаблен с `(group_id)` до `(group_id, title)` именно ради этого.
- Битые треды — это **родительские** треды с испорченным суффиксом. Их
  участники — исключительно `curator` + `parent` (ни одного `student`); у
  соседнего нормального треда той же группы — `curator` + `student`.
- Миграция 163 лечила title как `groups.name` **без суффикса** — то есть
  превращала родительский тред в точную копию title ученического. Именно
  это и уронило unique-индекс, а не факт существования дубля в исходных
  данных: **до миграции 163 пар с одинаковым `(group_id, title)` в базе не
  было ни одной.**

Миграция 164 поэтому чинит title «умно» — по составу участников треда
(есть `student` → без суффикса, иначе → `+ " — Родители"`), а не бланкетно.
После такого ремонта коллизий не остаётся ни одной (пересчитано на живых
данных перед записью файла).

## Что это значит для запуска 164

На проде миграция 164 фактически выполнит **только шаг 1** (умный ремонт
title трёх строк) — шаги 2 и 3 отработают, но не найдут кандидатов и не
изменят ни одной строки. Это ожидаемо и подтверждает, что причина сбоя 163
была именно в способе ремонта, а не в реальном дублировании данных.

Шаги 2/3 в файле оставлены не как «на всякий случай ради галочки», а как
защита от будущих похожих случаев (другая среда, повторный баг сидирования) —
описано подробно в комментариях самого SQL-файла.

## Как проверялось

Три раунда read-only запросов service-role клиентом (без записи):
1. Полный список `chat_threads` для группы `9afc95f3-…` + их `chat_participants`
   + счётчик `chat_messages` по каждому треду.
2. Поиск ЛЮБЫХ `chat_threads` с `title LIKE '%<U+FFFD>%'` независимо от `kind`
   (не только `group`) — подтверждено: все три — `kind='group'`.
3. Симуляция «умного» ремонта в JS (та же логика, что в SQL миграции 164) по
   всем шести group-тредам, с проверкой, остаются ли коллизии
   `(group_id, title)` после — результат: 0.
