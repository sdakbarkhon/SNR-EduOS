# План Z.2 — переделка админской панели

**Дата:** 06.08.2026 (обновлён после ответов заказчика на §6)
**Основание:** разведка админки 06.08 (23 проблемы, 7 критичных) + решение делать полную переделку, а не минимум.
**Принцип:** «разделить, а не заменять» — см. §5 отчёта разведки.
**Цель:** после Z.2 заказчик руками через админку создаёт реальную школу (учителей, учеников, родителей, предметы, группы) и всё работает корректно с первого раза.

Это **план**, не реализация. Ни строки кода, ни одной миграции по нему пока не выполнено.

## 1. Целевая модель

### Как сейчас

```
schools ──┬── groups ──────────────┬── student_groups ── students
          │     .subject   text NOT NULL  ← из захардкоженного списка 10 ключей
          │     .teacher_id uuid NULL ─────────┐
          │                                     │  ТРИ НЕЗАВИСИМЫЕ
          ├── subjects                          │  ТОЧКИ ПРИВЯЗКИ УЧИТЕЛЯ,
          │     .group_id  uuid NOT NULL ◄──────┤  которые ничем не связаны
          │     .name      text  ← русский текст, идентичность предмета
          │     .teacher_id uuid NULL ──────────┤
          │     UNIQUE(name, group_id)          │
          │                                     │
          ├── group_teachers ───────────────────┘   ← в неё НИКТО не пишет
          └── teachers .subject_slug text NULL       ← ЧЕТВЁРТАЯ, скрытая, RLS-предикат
```

Определение предмета (название, иконка, цвет) **сплавлено** со связкой «предмет в группе». Поэтому и определение, и выбор учителя приходится повторять на каждую группу.

### Как станет

```
schools ──┬── school_subjects              ← НОВОЕ: справочник предметов школы
          │     .school_id                    название/иконка/цвет живут ЗДЕСЬ
          │     .name, .icon, .color          UNIQUE(school_id, name)
          │     .is_active                    ← скрытие вместо удаления
          │     БЕЗ teacher_id  ← принципиально: см. ограничение ниже
          │        ▲
          │        │ catalog_id (nullable FK, НОВОЕ)
          │        │
          ├── subjects  ← ПЕРЕОСМЫСЛЕНА: это НАЗНАЧЕНИЕ «предмет × группа × учитель»
          │     .catalog_id → school_subjects
          │     .group_id   (как было)
          │     .teacher_id (как было — ЭТО и есть «кто ведёт»)
          │     .id         (НЕ МЕНЯЕТСЯ — на нём висят 127 уроков, 61 ДЗ, 15 планов)
          │
          ├── groups
          │     .subject     ← остаётся в схеме, UI перестаёт спрашивать
          │     .grade_level ← НОВОЕ: класс группы, источник правды для ученика
          │     .teacher_id  ← «куратор». В реальных школах поля в UI НЕТ (см. §6.1)
          │
          ├── group_teachers  ← начинает заполняться тем же action'ом, что subjects.teacher_id
          ├── parent_phone_codes ← НОВОЕ: коды подтверждения телефона (§5)
          └── teachers
                .subject_slug ← в реальных школах проставляется ВСЕГДА;
                                в демо остаётся как есть (NULL = куратор)
```

### Где что живёт после переделки

| Сущность | Где | Комментарий |
|---|---|---|
| **Справочник предметов школы** | `school_subjects` | Новая школа стартует с пустым. Создаётся админом, в т.ч. на лету из формы назначения |
| **Назначение «кто что где ведёт»** | `subjects` (строка на группу) | Один учитель = много строк = много предметов и групп. Уже работает |
| **Привязка учителя к группе** | `subjects.teacher_id` + `group_teachers` | Пишутся **одним** действием, больше не расходятся |
| **Куратор группы** | `groups.teacher_id` | Только демо-школа. В реальных школах роли нет |
| **Класс ученика** | `groups.grade_level` | Выводится из группы, отдельного поля в форме нет |
| **Предметник / куратор** | `teachers.subject_slug` | В реальных школах всегда заполнен. RLS-разделение по школам — Z.4 |

**Ограничение, которое стоит проговорить.** «Предмет — справочник школы, независимый от учителей» буквально означало бы перенос учителя на строку справочника. Так **потеряются данные**: у «Программирования» 4 строки под **двумя разными** учителями (проверено — это единственное такое название из 14). Поэтому справочник — без учителя, а учитель остаётся на строке назначения.

## 2. Разбивка на шаги

Порядок: **сначала то, что физически не может ничего сломать, потом то, что трогает живые предикаты RLS.** Аддитивные миграции раньше изменяющих; бэкфиллы — только по колонкам, которые не читает ни одна политика.

---

### Z.2.1 — Справочник предметов: схема (миграция 171)

**Что делает.** Создаёт `school_subjects` (с `is_active`) и RLS по образцу существующих политик `subjects`. Добавляет `subjects.catalog_id` — nullable FK. Бэкфиллит справочник из `DISTINCT (school_id, name)` и проставляет `catalog_id`. Помечает `is_active = false` у 13 предметов-стабов демо-школы (§6.3). UI не трогает.

**Закрывает:** фундамент под #2, #3; частично #15 (скрытие стабов).
**Миграция:** 171 (CREATE TABLE + ADD COLUMN + бэкфилл одной колонки).
**Риск: низкий.** Новая таблица + nullable-колонка. `subjects.id`, `teacher_id`, `name` не меняются → ни один FK и ни один RLS-предикат не задет. Триггер `trg_subject_teacher_direct_chats` объявлен `AFTER INSERT OR UPDATE OF teacher_id` — UPDATE только `catalog_id` его не будит.
**Зависимости:** нет. Первый шаг.
**Откат:** полный — `DROP TABLE` + `DROP COLUMN`.

---

### Z.2.2 — Справочник предметов: UI

**Что делает.** Разбивает `/admin/subjects` на два экрана: справочник школы (список + создать/переименовать/скрыть, **без обязательного выбора группы**) и назначения по группам. Переносит запись из браузерного клиента в server action с явным `school_id`. Убирает из формы группы захардкоженный список 10 ключей. Неактивные предметы не попадают в выпадающие списки.

**Закрывает:** #2, #3, #14, #15, #20.
**Миграция:** нет.
**Риск: средний.** Чисто UI, но скрытие/удаление должно уважать использование (см. Z.2.3).
**Зависимости:** Z.2.1.
**Откат:** да — вернуть старый экран, данные не пострадают.

### Z.2.3 — Гварды удаления и целостность

**Что делает.** Удаление предмета с уроками **запрещается**, вместо него предлагается «скрыть» (§6.9); в диалоге показывается честный счётчик «затронуто N уроков / M ДЗ / K планов». `deleteTeacher` начинает проверять все три поверхности привязки, а не только `groups.teacher_id`. `deleteParent` начинает удалять auth-пользователя.

**Закрывает:** #11, #12, #13.
**Миграция:** нет.
**Риск: низкий.** Только ужесточение проверок перед разрушительными операциями.
**Зависимости:** нет (можно параллельно с Z.2.1–Z.2.2).
**Откат:** тривиальный.

### Z.2.4 — Единая привязка учителя (ядро переделки)

**Что делает.** Новая вкладка «Предметы и группы» на странице учителя: все пары (предмет, группа), где он назначен, с добавлением и снятием. **Одно** server action пишет обе поверхности — `subjects.teacher_id` и upsert в `group_teachers`. В реальных школах `subject_slug` проставляется автоматически при первом назначении и никогда не остаётся пустым; в демо-школе поведение не меняется.

**Закрывает:** #1, #4, #5, #10.
**Миграция:** нет.
**Риск: высокий — самый опасный шаг плана.** Три причины:
1. Изменение `subjects.teacher_id` **будит триггер** `trg_subject_teacher_direct_chats`, порождающий личные чаты со всеми учениками группы. Только по одному назначению за раз, никаких массовых операций, обязательная проверка на демо.
2. `subject_slug` — живой предикат RLS. Для **демо-школы его значения не трогаем вообще**: у `teacher_karim` слаг NULL при 9 реальных предметах, и «починка» одним UPDATE переписала бы ему права.
3. `group_teachers.school_id` — `NOT NULL DEFAULT current_school_id()`, под service-role дефолт даёт NULL. Школу передавать явно.

**Зависимости:** Z.2.1.
**Откат:** частичный. Код откатывается, но созданные триггером чаты и записанные привязки остаются — нужен отдельный скрипт-компенсация.

### Z.2.5 — Бэкфилл существующих привязок (миграция 172)

**Что делает.** Приводит три поверхности демо-школы в согласованное состояние: заполняет `group_teachers` из объединения `subjects.teacher_id` и `groups.teacher_id`. Даёт `groups.subject` дефолт, чтобы форма могла перестать его спрашивать. Добавляет `groups.grade_level` и заполняет из имён групп (§6.6).

**Закрывает:** #10 (в данных), разблокирует #6 и #19.
**Миграция:** 172.
**Риск: низкий.** У `group_teachers` **нет ни одного триггера** (проверено), PK делает вставку идемпотентной, добавление строк только **расширяет** `is_my_teacher_group()` — отобрать доступ не может. `subjects.teacher_id` здесь **не переписывается**, чат-триггер молчит.
**Зависимости:** Z.2.4 (сначала код, умеющий поддерживать согласованность, потом выравнивание данных).
**Откат:** да — удалить добавленные строки по списку id.

### Z.2.10 — Логин уникален в пределах школы (миграция 175)

**Что делает.** Снимает глобальную уникальность логинов (§6.8), чтобы `ivanov` мог существовать в двух школах.

**Почему это не однострочник.** В БД уникальность уже правильная — `UNIQUE(school_id, username)`. Проблема в аутентификации: логин превращается в синтетический email `${username}@teachers.snr.local` **без участия школы**, а `auth.users.email` уникален глобально. При этом на форме входа пользователь вводит **только логин** — система физически не знает, в какой он школе.

**Предлагаемое решение (backward-compatible, без миграции существующих email'ов):**
- SECURITY DEFINER RPC `resolve_login(p_username)` возвращает список пар (school_id, email) по всем ролям.
- Одно совпадение → вход как сейчас, UX не меняется (это 100% случаев сегодня).
- Несколько совпадений → второй шаг «выберите школу», появляется только при реальной коллизии.
- Новые аккаунты получают email со школьным компонентом; **существующие не мигрируются вообще**.

**Закрывает:** #16.
**Миграция:** 175 (RPC).
**Риск: средний-высокий.** `signInWithUsername` вызывается из **пяти** мест, включая `apps/mobile` (заморожен) и `apps/h5p`. Менять её сигнатуру нельзя — только расширять поведение, сохраняя текущий путь рабочим.
**Зависимости:** нет технических, но лучше последним из кодовых шагов.
**Откат:** да — RPC не используется, старый путь остаётся.

> **Можно безболезненно отложить.** Коллизия физически невозможна, пока населена только одна школа. Если решите вынести в Z.4 — ничего не блокируется.

## 3. Что трогать нельзя

### `teachers.subject_slug`
Выглядит косметической подписью, на деле — **живой предикат RLS**. Через `is_curator_teacher()` (буквально `subject_slug IS NULL`) входит в SELECT-политику `lessons`: `is_subject_owner(subject_id) OR (is_curator_teacher() AND is_my_teacher_group(group_id))`. Плюс миграция 154 гейтит по нему библиотеку кафедры.

**Проверено:** функция **не знает про школу вообще** — в ней нет ни `school_id`, ни `current_school_id()`. Поэтому «куратор только в демо» на уровне RLS невозможен без правки самой функции → это Z.4 (см. §6.1).

**Что сломается при неаккуратной правке:** массовая простановка слага существующим учителям **сузит** видимость уроков; массовое обнуление — расширит. **Дропать колонку в Z.2 запрещено.**

### `subjects.teacher_id`
Это и есть `is_subject_owner()` — единственный предикат, гейтящий **каждую** запись урока учителем. На `subjects.id` завязаны 127 уроков, 61 ДЗ, 15 планов (0 NULL-ов).

**Что сломается:** перенос учителя на другую таблицу или смена `subjects.id` переписывает право записи для 100% живого контента одной миграцией. **Не переносим, не пересоздаём, не меняем id.**

### `groups.subject`
`text NOT NULL` **без дефолта** — просто перестать писать нельзя, INSERT упадёт. Смысла нет (у всех 4 групп литерал `'programming'`), но убирать в Z.2 не нужно: дефолт + перестать спрашивать в UI.

### Триггер `trg_subject_teacher_direct_chats`
`AFTER INSERT OR UPDATE OF teacher_id ON subjects` — на каждое изменение учителя пробегает всех учеников группы и заводит личные чаты. Короткое замыкание есть (`NEW.teacher_id IS NOT DISTINCT FROM OLD.teacher_id`), поэтому идемпотентный бэкфилл бесплатен. **Но любое реальное переназначение массово порождает чаты.** Правило: по одному, осознанно; массовых UPDATE по `teacher_id` в Z.2 нет.

### `signInWithUsername`
Вызывается из пяти мест, включая замороженный `apps/mobile` и `apps/h5p`. В Z.2.10 её поведение расширяется, **сигнатура и существующий путь сохраняются**.

### Чего ещё не трогаем
`apps/mobile` (заморожен), StageMedia (пауза, незакоммичен), заморозка времени, правило «1-completed / 2-in_progress / 3+ ручной», отключённый morning-lesson-cycle, миграции 132–170.

## 4. Демо-школа: что с ней станет

Текущее наполнение (проверено 06.08): **29** строк `subjects` → **14** уникальных названий, из них **13 стабов с нулевым использованием**; **4** группы; **7** учителей; **30** учеников; **1** родитель; **127** уроков; **61** ДЗ; **15** учебных планов; **18** строк `group_teachers`; **1** связка родитель-ребёнок.

## 5. Родительский поток

### Что сломано сейчас
Поток мёртв на всех трёх звеньях: `createParent` создаёт `parents` с `user_id = NULL` и код в `parent_invites`; страницы погашения `/parent/join` **не существует**, `verifyParentInvite`/`completeParentJoin` имеют **ноль вызовов**; реальный вход — захардкоженная карта из 3 телефонов с общим паролем `parent2026` и непроверяемым СМС-кодом. `parents.phone` в аутентификации не участвует. Живьём: 1 родитель, 0 инвайтов.

### Решение: телефон как логин + пароль от админа + реальный код подтверждения с заглушкой доставки

Админ создаёт родителя: ФИО, телефон, пароль (генерируется и показывается один раз, как для админов школ в `/superadmin`), дети — множественный выбор. Телефон становится ключом входа: `parents.phone` → NOT NULL + UNIQUE, auth-пользователь создаётся с производным email по схеме остальных ролей. Хардкод трёх телефонов удаляется.

**Почему телефон, а не искусственный логин.** Родители заходят с мобилки, и телефон — единственный идентификатор, который они помнят без подсказки. Экран ввода телефона **уже существует** и на вебе, и в мобильном приложении, так что UX не меняется — меняется лишь то, что за ним стоят реальные данные, а не константа в коде.

### SMS-верификация: заглушка, которую заменяет одна функция

Из двух вариантов («принимать любой код» против «генерировать реальный, доставку заглушить») выбран **второй** — он чище по одной причине: при «любом коде» путь проверки никогда не исполняется, и в день подключения провайдера он окажется непротестированным, а до тех пор это открытая дыра, про которую все забудут.

Устройство:
- Таблица `parent_phone_codes` (телефон, хеш кода, срок жизни, число попыток, отметка использования).
- Код генерируется и проверяется **по-настоящему** с первого дня: срок жизни, лимит попыток, одноразовость.
- Доставка изолирована в **одну** функцию `sendSms(phone, text)`. Сейчас её реализация пишет код в лог сервера и в ту же строку БД, чтобы админ мог продиктовать его родителю. Подключение провайдера = замена тела этой функции, больше ничего.
- Код виден админу в карточке родителя (пока нет провайдера) — это осознанный временный компромисс, который снимается вместе с заглушкой.

**Демо-родителя не трогаем** — ему проставляется телефон, и он продолжает входить.

**Что учесть.** Изменение затрагивает `apps/mobile-parent` (убрать хардкод, ходить в реальную auth) — приложение вне обычных границ задач, нужно отдельное согласование перед Z.2.8.
